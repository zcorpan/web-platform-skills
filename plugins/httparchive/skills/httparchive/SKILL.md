# httparchive

## Common Crawl first

- For anything answered from response bodies (markup patterns, parser changes, inline CSS/JS), start with Common Crawl WARCs: free, no account, quick to iterate. Look for local copies first (e.g. `~/git/commoncrawl/cc-data/<crawl>/`, see its `MANIFEST.md`; else ask the user where they keep them) and reuse or extend that seeded pick instead of downloading a new set.
- Otherwise `template/cc.py` downloads a seeded random set of a crawl's WARCs (list: `https://index.commoncrawl.org/collinfo.json`) into the shared data directory; `html_responses()` iterates the HTML responses (`warcio`). A WARC is ~1 GB with ~21k HTTP 200 `text/html` responses; 12 (~250k pages) resolve rates down to ~0.01%. Prefilter bodies with a cheap regex, then parse in a multiprocessing pool with a per-page timeout.
- Common Crawl has every crawled URL, not just root pages, and no rank, use counters, or custom metrics. Prototype classifiers and find the patterns that matter there, then run one HTTP Archive query for root-page rates and rank strata. Say which corpus each number comes from.
- For a few known URLs, the CDX index (`https://index.commoncrawl.org/<crawl>-index?url=<url>&output=json`) gives `filename`, `offset` and `length` for an HTTP range fetch of one record.

## Cost

- Queries bill the user's Google Cloud project. Before the first non-dry-run query, show the dry-run estimate and wait for explicit approval, even if the user asked for HTTP Archive data, and especially if this skill loaded on its own. Ask again for any query above an approved budget or per-query cap.
- Give estimates in TiB with on-demand cost at $6.25/TiB (e.g. "0.104 TiB, about $0.65"). Dry-run every query (`--dry_run`) and always pass `--maximum_bytes_billed`.
- Cost is columns read, not rows returned: `LIMIT` doesn't reduce it, `TABLESAMPLE SYSTEM (n PERCENT)` does. One `custom_metrics` sub-field over all root pages costs far less than `payload` or the `requests` table (~200 TiB per crawl date in 2026).
- The dry-run number is an upper bound, and `--maximum_bytes_billed` is checked against it before the query starts. `TABLESAMPLE` and filters on later clustering columns (`type`, `rank`) don't lower it, so a sampled or filtered query is rejected unless the cap covers the full estimate; a `client` filter does lower it. A `type` filter didn't lower bytes billed for `response_body` either.
- Prototype on a sample, then run the full query once. 1% is fine for small columns. For `response_body`, prototype on `httparchive.sample_data.requests_10k` (also `pages_10k`, `parsed_css_10k`: ~10k root pages per client, recent crawls); a sampled `crawl.requests` query's cap must cover its full estimate, so get approval for that cap.
- Actual cost is in job stats (`bq ls -j --format=json`, `statistics.query.totalBytesBilled`); `-a` includes other users' jobs, so filter on `user_email`.
- For `response_body` work, scan once into a scratch table in the user's project (page, rank, matched snippets or blocks, and the body only for candidates) and aggregate from it. Every query reading its body column bills the whole column again; copy the rows you need into a small table once. Download with `bq head --format=json --start_row=N --max_rows=M`, a few in parallel (tabledata.list, not billed as a query). Ask before deleting scratch tables when done; within the time-travel window (7 days by default), `bq cp dataset.table@<epoch_ms> dataset.table` restores one.

## Querying

- Setup: `bq` comes with the Google Cloud CLI (`brew install --cask gcloud-cli` on macOS); `gcloud auth login`, then set a default billing project. Docs: https://har.fyi/.
- Pass SQL on stdin (`bq query --use_legacy_sql=false < q.sql`); a leading `--` comment in an argument parses as a flag.
- `TABLESAMPLE` differs each run. For a reproducible sample, order by `FARM_FINGERPRINT(CONCAT(page, '<seed>'))` and take the first N, per stratum with `ROW_NUMBER() OVER (PARTITION BY ...)`.
- Substring hits in `response_body` are often name lists (minifiers' and obfuscators' reserved DOM names, e.g. terser's `domprops`; fingerprinting lists). Return `FARM_FINGERPRINT(response_body)` and regex snippets around the match, classify each distinct body, and fetch live copies (untrusted) when snippets aren't enough. By default keep list hits and check them in a browser, since a listed name can still be looked up or called. When that's impractical (a common string with too many hits), exclude known lists in the query (e.g. a regex on neighboring names) and say so with the result.
- Regex prefilters over bodies are supersets (markup inside JS strings, escaped `\"`, `<\/`, matches too): confirm on the full document with a real parser before counting. Extraction matches don't overlap, so context captured after one match hides a match starting inside it; measure the prefilter's recall on a corpus you can parse exactly (e.g. local WARCs) and report it.
- Compare full values, never stored snippets: truncation for storage or display hides differences past the cut.
- Crawled bodies can be truncated (often at a power of two). A result depending on the document's end (an element still open at EOF) counts only if the body ends with `</body>` or `</html>`; report the rest as artifacts.
- `STRING()`, `BOOL()`, etc. throw on wrong-typed values, which a full-table run can hit when a sample didn't. Use `LAX_STRING()`, `LAX_BOOL()`, `SAFE.INT64()`. Quote hyphenated JSON keys: `'$."responsive-images"'`.

## Use counters

- Look for an existing counter before writing a query: Chromium `third_party/blink/public/mojom/use_counter/metrics/web_feature.mojom` (and `css_property_id.mojom`), Gecko `dom/base/UseCounters.conf`.
- Read where it's incremented before trusting it: it may fire on feature detection or on cases the change doesn't affect, or miss ones it does; counters for the same feature can differ by orders of magnitude.
- Chrome rates (% of page loads): `https://chromestatus.com/metrics/feature/timeline/popularity/<id>`, JSON at `https://chromestatus.com/data/timeline/featurepopularity?bucket_id=<id>`. Daily values are noisy and seasonal; look at months. Gecko rates: `use.counter.*` Glean metrics in GLAM.
- Field rates (% of page loads) include pages the crawl misses (logged-in, intranet, deep links). A field rate far above the crawl rate (% of pages) may mean the crawl undercounts or the feature is on a few heavily used pages; say so with the estimate.
- `pages.features` lists the Blink counters each page hit (`feature`, `id`, `type`: `default` or `css`). When one matches the change, find pages to review with `EXISTS(SELECT 1 FROM UNNEST(features) WHERE id = '<id>' AND type = 'default')`. Crawls before the counter reached Chrome stable lack it. The crawl only loads pages, so counters needing interaction (clicks, typing, form submission, navigation) or firing late are missing; there, an empty or low count isn't evidence of low usage.
- Once a removal or behavior change reaches Chrome stable, later crawls run with it, and counters that fire only on the old behavior go quiet. Use crawls from before it shipped.

## Custom metrics

- Read the metric's source (HTTPArchive/custom-metrics, `dist/<name>.js`) before using a field: what it measures, when (in Chrome, after load, at the crawl's viewport), how derived fields are computed.
- Derived fields can share an input (e.g. an "error" from the metric's own parse of an attribute), so seemingly independent conditions can be one signal. Prefer fields read straight from the DOM.
- Metric parsers lag the spec (new keywords, syntax). Check parse-error fields; exclude or count those cases separately.
- Look at ~20 flagged examples before trusting a count: hidden elements (`clientWidth` 0), min/max clamping, pages changed since the crawl.

## Estimating compat impact

- State the denominator: crawl date, client, root pages only (`is_root_page`) or all, and "pages with at least one X" vs all pages.
- Stop early when partial data already rules out shipping (e.g. a sample query or the first reviewed pages show that much breakage): say so and ask whether to write up the data so far or continue. Concluding a change is compatible needs the full check.
- Treat the proposed change as one option. When data shows breakage, find the cause and whether a variant avoids it while meeting the change's goal. Write the goal down (e.g. a security property) and check each variant against it, not only compat. Measure promising variants side by side in one pass and say which you'd recommend and why; the user and spec editors decide.
- The crawl visits root pages plus one linked page per site, so resources mostly reached by direct URL (feeds, sitemaps, API endpoints, standalone documents) are underrepresented. If usage concentrates there, say the crawl can't size it and look for other evidence.
- Where crawl data can't decide, use separate "definitely changes" and "might change" buckets rather than guessing.
- Check the estimate on a seeded, stratified random sample (~100 per bucket) loaded live in a browser matching the crawl (Chrome; mobile viewport 360px wide).
- Before emulating, look for an existing switch: Chromium runtime features (`--disable-blink-features=<Name>`, `--enable-blink-features=<Name>`, from `runtime_enabled_features.json5`) or `--disable-features=<Name>`, Firefox prefs (`StaticPrefList.yaml`). Check it takes effect in your build.
- Otherwise emulate on a current engine by rewriting the page so the old algorithm produces the new result. If that's impossible or approximate (e.g. timing, parsing, loading changes), ask the user for a build implementing the change and compare it against an unmodified build of the same version.
- For an HTML parser change, patch a spec-following parser (e.g. html5lib) per variant, parse each candidate page both ways, and compare per element. Check the patch against the engine build on edge cases (again after every fix) before trusting its counts.
- For a Gecko change, test in Firefox. Playwright's Firefox is patched and can't drive a local build; use Selenium with geckodriver and `enable_bidi` (JS errors via `script.add_javascript_error_handler`, console via `add_console_message_handler`, preload scripts via `script.pin`). Exclude CSP reports when comparing errors; they carry random tracking URLs.
- To emulate removing a WebIDL member in Gecko, add `Pref="..."` plus a `StaticPrefList.yaml` entry (`RelaxedAtomicBool`, `mirror: always`, so workers can read it), and build in a git worktree with its own objdir. Extension content scripts can't emulate it: they don't run in workers.
- Gecko use counters work as a detection pass: with `dom.use_counters.dump.{document,page,worker}` set, Firefox prints `USE_COUNTER_<KIND>: <metric> - <url>` to stderr when the document is destroyed. Open each page in a new tab, close it, and read the new stderr lines (geckodriver's `log_output`). Dedicated workers' deprecated-operation counters land on the ancestor document; shared and service workers have none. Run detection over every hit, then compare before and after on the pages that hit. Counters fire only on calls; to also catch feature detection, a preload script can swap the member for a logging accessor (main thread only).
- `compare.py` measures before twice (A, then A2) and after (B); A vs A2 differences are page noise (carousels, animations, ads).
- Client-side frameworks re-render server markup after hydration, so a final-state screenshot can hide a parse difference. For parse-time changes, also capture an early state (e.g. `DOMContentLoaded`), or say only the final state was seen.
- Review changed pages by eye, cropped around the changed element (whole page when the whole document changes). Rate each broken, worse, neutral, improved, no visible change, or not assessable (consent dialog, blank page). Rate against the page's purpose: a machine-readable resource (feed, sitemap, API) losing its human-facing presentation is worse, not broken. A changed layout isn't breakage, and improvements don't offset breakage.
- Extrapolate per stratum, (hits / sample size) × stratum size, summed. With only 1 or 2 hits, give exact binomial intervals.
- Visual comparison misses effects that don't render: scripts reading changed nodes, ids or form controls in hidden content, fetches, serialization, errors. Check them only when the change alters what scripts can observe (DOM shape, API results, what's fetched) and the visual results don't settle it; skip for purely presentational changes or when visuals already show incompatibility. It's costly (a trace run plus code review per call site), so say what it adds before starting. When warranted, cover every page that hit:
  - Trace at runtime in each behavior with a preload script (all frames) that wraps the APIs whose results change, marks differing nodes, and logs what scripts do with them: queries (with result counts, to compare between behaviors), serialization, text reads, clones, insertion into the live document, fetches, and errors with stack frames. Check it first on a local test page exercising every entry point and consumer in each behavior.
  - Group events by entry point and calling script (normalize hashes and per-site IDs in script URLs) and class each group by what was observed. Code-review every group where scripts used the changed result, plus a seeded sample of the other classes; if the sample finds misses, widen the review to that whole mechanism.
  - Build one dossier per group (trace events from both behaviors, beautified code around each stack frame, kept out of the repo) and give reviewers a written brief with a verdict per comparison: none, invisible (tracking or data never shown), benign (visible to scripts or the network only), user-facing, or unclear with a concrete test. Run those tests and confirm every user-facing verdict in the build.
  - Give each page its most significant group verdict, extrapolate the random sample like the visual ratings, and report pages the trace couldn't see separately.
  - Watch for content hidden from rendering but still live DOM (ids, labels, form controls, default buttons, stylesheets, fetches), APIs exposing one result through several getters (XHR `response` and `responseXML`), code using another realm's APIs the preload script doesn't reach, and stack frames losing line numbers when URL queries are scrubbed (extract positions first).
- If the sample has few or no top-ranked pages (`rank`), run every top-ranked hit through the same steps and report them separately.
- In a custom harness, wrap each visit in an overall timeout (e.g. `asyncio.wait_for`) and record a timeout as an error: `page.evaluate` and `context.close` have no timeout, so one hung page holds a slot forever and stalls the run.

## Finding bugs in an implementation

- The same live comparison tests one implementation against a reference: a polyfill or extension vs native, a flag or pref flipped, a new build vs release, one browser vs another. A and A2 run the reference, B the candidate. The output is bugs to file, not an estimate; nothing to extrapolate.
- If the feature is common enough that top-ranked pages alone give a usable sample, sample those, so the most-visited sites are well covered; add a long-tail sample if the long tail seems to use it differently. Otherwise use every page known to exercise it (e.g. an earlier compat run's sample, top-ranked and follow-up pages). Either way, include pages not rated affected: a polyfill changes feature detection, so unaffected-looking pages take new code paths.
- Have the sanity check confirm each side runs the intended implementation (e.g. the global is native in A and the polyfill's in B), not only that the feature works.
- In Chromium, set `AFTER_EXTENSION` in `change.py`. In Firefox, install it per session with geckodriver (`install_addon(path, temporary=True)`), the pref in the session's options.
- Flag console errors and warnings only B logs, not just exceptions: polyfills often log failures instead of throwing. Ignore the setups' by-design messages. Also flag states only the candidate has (a loading indicator still up, raw content where A rendered).
- Before blaming the candidate, check the page didn't fail on its own: reload in both setups and look at the responses (server errors, rate limiting, bot blocks). When the candidate needs the native feature off, also load failing pages with it off and no candidate; a failure there is the engine's (its disabled path), so reduce it and report it to the engine. When comparing browsers, or for a polyfill targeting several, check what each engine actually does; the reference can differ between them.
- Pages cover only what they happen to exercise. Read the candidate's code for where it differs from the reference by design (refetching instead of using the loaded response, running in every page and frame, its own stylesheet, a different document type or realm) and write a test page per difference, covering cases the pages may lack (non-GET loads, non-UTF-8 encodings, CSP, frames, scripts in the source). Also measure its cost on pages that don't use the feature.
- Reduce each cause to a minimal local test page, run it in every browser in both setups, and commit the pages, runner, and output. Link the responsible code, and the engine or spec code defining the expected behavior, at a commit.
- Size each cause on the run's pages ("N of M") by scanning the reference's output or the raw responses for its trigger. Commit the scans and a script recomputing every count the issues cite; rerun it before publishing.
- Before suggesting a fix, prototype it in the candidate and run the test pages in each browser; if it doesn't work, say so in the issue instead. For a small working fix, offer a PR alongside the issue.
- Search the tracker for existing reports first. File one issue per cause, every title sharing a tag (e.g. the research repo's name). Each gives what's wrong, the test case, a few affected pages with review images, and a hedged fix suggestion. Draft them; file only when asked. The README gives the method, counts flagged per browser, and searches for the tag, not the bug list.

## Research repo

- Build a reproducible repo as you go: copy `template/` from this skill's directory to `/tmp/<feature>-compat-<issue>/`, `git init`, and `git config core.hooksPath hooks` so every commit runs `publish_check.py --staged`. Before the first live page load, write the tester's public IP, city, region, country name, and demonym to `.publish-terms` (gitignored, one per line; the hook blocks commits until it exists); add the new IP if the network changes mid-run. Keep queries and their output, sample, scripts, logs, and review images there, so it can be moved and pushed as is. Create or push a GitHub repo only when asked.
- The template drives Chromium; for Firefox, rewrite `harness.py` with Selenium as above. Put the change in `change.py` (before/after setup, sanity check, extra measurements, change-specific auto-ratings); `harness.py`, `compare.py`, `analyze.py`, `recheck.py`, `sample.py`, `extrapolate.py`, and `cc.py` are generic. Adapt them when needed and commit the versions that produced the data; if a script changed mid-run, say so in the README.
- Fill in `README.md` from the template's structure. Take every number from a committed file; before publishing, rerun `analyze.py` and `extrapolate.py` on the committed data and recount the README's numbers from the files.
- Leave out billing project, account, job IDs, and costs; give bytes processed per query. Don't commit raw tool output (`bq` stderr, driver or browser logs). Screenshots stay out (`.gitignore`); commit the review images ratings rely on.
- Live-load output can identify the tester: the public IP (block and captcha pages print it), tracking IDs and tokens in URLs and payloads, country-specific hosts (`google.se`), and geo-targeted page text, titles, ads, and final URLs. Scrub at capture like `scrub()` and `scrub_record()` in `harness.py`; custom harnesses need the same. Keep only the fields and console or error text the analysis needs.
- Screenshots can show location too (geo-targeted ads, region or currency pickers). Commit crops around the change rather than full pages where they suffice. The pre-commit hook OCRs staged images with `ocr_check.py` against `.publish-terms` and IP addresses; drop or redact hits. OCR misses purely visual hints (flags, maps, logos), so also look at a sample by eye. Don't have an agent read every image: run `ocr_check.py` first and send only hits and a small sample.
- Before every push, run `publish_check.py` without `--staged`. It scans every blob in history; resolve each hit (scrub, drop, or confirm it's crawl data or harmless) and rewrite history before pushing. When scrubbing existing output, rerun the analysis and check its outputs don't change (e.g. stack URLs it parses). Once pushed, force-pushing isn't enough: GitHub serves old commits by SHA until the repo is deleted and recreated (ask first), and the data may already be copied.
- When asked to publish, don't run the commands yourself: give the user each to run as `! <command>`, waiting for its output before the next: create the repo and push (`gh repo create <owner>/<repo> --public && git remote add origin git@github.com:<owner>/<repo>.git && git push -u origin main`, in the repo), then post the comment (`gh issue comment <N> --repo <owner>/<repo> --body-file <file>`, body written to the file first).

## Reporting findings

- Draft the comment for the spec issue or bug in chat; post only when asked. Open with a short paragraph in the user's voice: what was checked and the verdict, with the headline number. Then `AI summary of the research ([<owner>/<repo>](<repo URL>)):` and the summary as one block quote, every line starting with `>` (bare `>` for blank lines between paragraphs and lists).
- Keep the summary under ~250 words; the README holds the rest. Four parts:
  - Method in two or three sentences: setup (builds or emulation, and its sanity check against real browsers), denominator (crawl date, client, pages with the counter or condition), samples.
  - Results as one small table: a row per comparison, extrapolated counts per verdict (intervals only where they carry the conclusion).
  - Affected pages, one line each: site, what changes for users, link to the review image. Only pages rated worse, improved, or with a user-facing change.
  - A closing link to the README.
- Leave out per-sample and per-stratum breakdowns, "not covered" lists, why pages were unaffected, neutral cases not bearing on the verdict, and process details (how review was split, what was rechecked). Take every number from committed files.
- When comparing options, focus on the recommended one and point to the README for the others in one line.
- If a posted number turns out wrong, correct it in the comment.
- Link each affected page's evidence to its committed review image (`https://github.com/<owner>/<repo>/blob/main/<path>`), not the live site, which changes and sends readers to an arbitrary site; say once which side of a crop or panel is which. Name the site in plain text.
